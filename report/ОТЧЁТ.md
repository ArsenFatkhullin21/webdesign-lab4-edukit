# 2. Описание дизайн-системы

**Название:** EduKit. **Бренд и продукт:** образовательная платформа — онлайн-школа программирования CodeLab из лабораторных работ №2–3. **Характер:** спокойный, деловой и дружелюбный. Синий акцент, скругления 8–16 px, заголовки Manrope и текст Inter.

**Целевые продукты:**

- публичный сайт школы;
- личный кабинет студента (расписание, задания, прогресс);
- административная панель управления потоками и заявками.

Принципы дизайн-системы:

1. **Ясность.** Компонент понятен без инструкции: видимые подписи полей, явные состояния (hover, focus, disabled, error).
2. **Консистентность.** Одинаковые элементы выглядят и ведут себя одинаково; в CSS компонентов нет «жёстких» цветов — только токены.
3. **Доступность.** Соответствие WCAG 2.1 AA: контраст ≥ 4.5:1, видимый фокус, полная работа с клавиатуры, `prefers-reduced-motion`. Проверяется автоматически (раздел 8.2).
4. **Адаптивность.** Компоненты работают от 320 px: подвал перестраивается, таблица прокручивается по горизонтали.
5. **Расширяемость.** Новые варианты добавляются модификаторами `ds-*--variant` без изменения существующего API; изменения версионируются по SemVer.

# 3. Дизайн-токены

## 3.1. Структура и формат

Токены описаны в формате **W3C Design Tokens (DTCG)**:

- значение задаётся полем `$value`, тип — полем `$type`;
- ссылка на другой токен — синтаксис `{color.primitive.blue.600}`.

В примере методички используются поля без `$` — это более старый формат Style Dictionary 3. В работе применён актуальный формат спецификации DTCG; Style Dictionary 5 читает его при `usesDtcg: true`.

```
tokens/
├── colors.json        примитивы + семантические роли
├── typography.json    семейства, размеры, начертания, межстрочный
├── spacing.json       шкала отступов (шаг 4 px)
├── radii.json         скругления
├── shadows.json       тени (DTCG-объекты)
├── motion.json        длительности и cubic-bezier
└── themes/dark.json   тёмная тема — только переопределения
```

Таблица: Группы токенов EduKit {#tab:tokens}

| Группа | Файл | Состав |
|---|---|---|
| Цвета: примитивы | colors.json | blue 50–900, gray 50–900, green, amber, red, white, black |
| Цвета: семантика | colors.json | background (default, surface, subtle, overlay), text (default, muted, inverse), border, action (primary, link, danger и др.), feedback (info, success, warning, error), focus.ring |

## 3.2. Генерация CSS через Style Dictionary

Конфигурация `style-dictionary.config.mjs` (рисунок @fig:sd-config) выполняет две сборки:

- **светлая тема** — все токены попадают в `src/styles/tokens.css` под селектором `:root`;
- **тёмная тема** — базовые токены подключаются через `include` (они нужны, чтобы разрешить ссылки), но в файл `tokens-dark.css` попадают только токены из `themes/dark.json` (фильтр `isSource`).

Опция `outputReferences: true` сохраняет связи: семантические переменные ссылаются на примитивные через `var(...)`, а не на «вшитые» значения (рисунок @fig:css-sem).

# 4. Атомарный дизайн

Компоненты разложены по уровням методологии Брэда Фроста. Молекулы и организмы собираются из атомов:

- Form = FormField × 2 + Radio + Checkbox + Button;
- Card = Badge + Button + Avatar;
- Header = Icon + Button;
- Table = Badge.

# 5. Реализация компонентов

Каждый компонент лежит в отдельной папке `src/components/<уровень>/<Имя>/` и состоит из трёх файлов:

- `<Имя>.js` — функция-фабрика, возвращающая DOM-элемент;
- `<Имя>.css` — стили по BEM с префиксом `ds-`, только токены;
- `<Имя>.stories.js` — истории Storybook.

В отличие от примера методички, разметка собирается не через `innerHTML` с подстановкой строк, а через хелпер `h()`. Пользовательский текст попадает в DOM как текст, а не как HTML, что исключает XSS.

# 7. Версионирование

Дизайн-система версионируется по **Semantic Versioning**:

- **MAJOR** — несовместимые изменения (удаление компонента, изменение API);
- **MINOR** — новая функциональность без поломок (компонент, вариант);
- **PATCH** — исправления.

Текущая версия **1.1.0** — MINOR-обновление относительно 1.0.0. В неё вошли тёмная тема, компоненты Switch, Tooltip, Modal и Table, а также вариант `danger` у Button. Ни одно существующее API при этом не сломано. История изменений ведётся в `CHANGELOG.md` в формате Keep a Changelog. Релиз отмечен аннотированным git-тегом `v1.1.0`, отправленным на GitHub.

## 8.3. Задание 3 — визуальное регрессионное тестирование

**Настройка CI.** Workflow `.github/workflows/chromatic.yml` (рисунок @fig:chromatic-yml) запускается при каждом push:

1. устанавливает зависимости и генерирует токены;
2. публикует Storybook в Chromatic, если в репозитории задан секрет `CHROMATIC_TOKEN`.

`fetch-depth: 0` нужен, чтобы Chromatic видел историю git и находил базовую сборку для сравнения. Пока секрета нет, шаг пропускается, и сборка остаётся зелёной (рисунок @fig:gh-actions).

![.github/workflows/chromatic.yml](screens/code--github-workflows-chromatic-yml.png){#fig:chromatic-yml width=85}

**Эксперимент с изменением компонента.** Чтобы показать механизм визуальной регрессии, написан локальный аналог Chromatic — `tools/visual-regression.mjs`. Он делает следующее:

1. снимает все 86 историй в двух темах (172 снимка);
2. сравнивает каждый снимок с эталоном попиксельно (библиотека pixelmatch);
3. для каждого изменившегося снимка сохраняет diff-изображение.

Изменение: в `tokens/colors.json` цвет `blue.600` заменён с `#2563EB` на `#DC2626`, после чего Storybook пересобран.

**Как автоматическое тестирование помогает не допустить регрессий:**

- Изменение одного токена затрагивает десятки компонентов, вручную их не проверить: правка одного цвета задела 75 из 172 снимков — кнопки, ссылки, Badge, Pagination, Tabs, Header, Form и Modal в обеих темах.
- Визуальный тест показывает каждое затронутое место на diff-изображении до слияния изменений.
- В Chromatic каждое изменение нужно явно принять или отклонить в Pull Request, поэтому непреднамеренное изменение не попадёт в основную ветку незамеченным.

# 9. Вывод

**Чем дизайн-система отличается от набора компонентов в одном проекте.** В лабораторной работе №2 стили лежали внутри сайта и были привязаны к его страницам. EduKit — отдельный продукт со своими атрибутами:

- единственный источник истины — токены в JSON;
- компоненты, не знающие о страницах конкретного сайта;
- документация, версии, история изменений и автоматические проверки.

Её можно подключить в новый продукт, не копируя CSS. Смена темы и смена фирменного цвета выполняются правкой JSON, без изменения компонентов — это подтвердил эксперимент из раздела 8.3.

**Как Storybook помогает команде разработки:**

- каждый компонент и каждое состояние видны изолированно — включая hover и focus, которые на живом сайте трудно воспроизвести;
- `argTypes` дают панель параметров и автоматическую таблицу API;
- аддон a11y сразу показывает нарушения доступности;
- истории одновременно служат документацией, песочницей и основой визуальных тестов.

**Что оказалось самым сложным:**

1. Собрать тёмную тему как отдельный набор токенов: базовые токены должны участвовать в разрешении ссылок, но не попадать в выходной файл (`include` + фильтр `isSource`).
2. Формат DTCG не совпал с примером методички (`$value`, объектные тени).
3. Автоматическая проверка нашла проблему контраста 4.07:1, которую глазом не заметить.

# 10. Ответы на контрольные вопросы

1. **Дизайн-система** — продукт из токенов, компонентов, правил использования, документации и процессов (версии, ревью, тесты). **UI Kit** — только набор визуальных элементов без правил и процессов.
2. **Atomic Design** — методология Брэда Фроста с пятью уровнями: atoms (кнопка, поле) → molecules (поле формы) → organisms (шапка, форма) → templates (скелет страницы) → pages (шаблон с реальными данными).
3. **W3C Design Tokens** — стандарт описания токенов в JSON: `$value`, `$type`, ссылки `{group.token}`, составные типы (shadow, typography). Важен тем, что один формат понимают Figma-плагины, Style Dictionary и другие инструменты — токены переносятся между дизайном и кодом без ручной синхронизации.
4. **Style Dictionary** — инструмент сборки, превращающий токены в переменные для разных платформ (CSS, SCSS, JS, iOS, Android). Решает задачу единого источника истины для всех платформ.
5. **Примитивный токен** хранит «сырое» значение (`blue.600 = #2563EB`). **Семантический** описывает роль (`action.primary`) и ссылается на примитив; тема и бренд меняются подменой ссылок.
6. **Storybook** — среда разработки и документирования UI-компонентов в изоляции. Он даёт каталог компонентов, интерактивные параметры, автодокументацию, проверку доступности и основу для визуальных тестов.
7. **Story** — одно конкретное состояние компонента (например, `Button / Disabled`). **Args** — входные параметры истории; их можно менять в панели Controls, и компонент перерисовывается в реальном времени.
8. **Chromatic** — облачный сервис от создателей Storybook. Он хостит Storybook, выполняет визуальные тесты всех историй при каждом коммите и организует ревью изменений (принять / отклонить) в Pull Request.
9. **Визуальное регрессионное тестирование** — автоматическое сравнение скриншотов компонентов до и после изменения, чтобы поймать непреднамеренные изменения внешнего вида.
10. **SemVer** — версия вида MAJOR.MINOR.PATCH. MAJOR — несовместимые изменения API, MINOR — новая обратно совместимая функциональность, PATCH — обратно совместимые исправления.
